# SaaS Gaming Application

A multi-tenant SaaS gaming application built for the EKS Platform Engineering workshop. This application demonstrates how to build a scalable, cloud-native gaming platform using Amazon EKS, S3, and DynamoDB.

## Features

- Simple interactive web-based game
- **AI Game Host** — natural-language, tier-specific clues generated by Amazon Bedrock
- Player avatar management with S3 storage
- Game state persistence with DynamoDB
- Leaderboard functionality
- Multi-tenant ready with namespace isolation
- Health check endpoints for Kubernetes
- Graceful shutdown handling

## Architecture

The application consists of:
- **HTTP Server**: Express.js server handling game API and static content
- **Game Logic**: Core game state management (deterministic win/lose/score engine)
- **AI Game Host**: Amazon Bedrock integration that phrases a clue for the next guess (see [AI Game Host](#ai-game-host-amazon-bedrock))
- **S3 Integration**: Player avatar storage
- **DynamoDB Integration**: Game state, player data, and leaderboards

## AI Game Host (Amazon Bedrock)

The **AI Game Host** is an agentic feature that turns the guessing game's plain
`too high` / `too low` feedback into a natural-language clue generated by an
[Amazon Bedrock](https://aws.amazon.com/bedrock/) model. It showcases how a
SaaS platform can layer generative AI onto an existing application **per tenant
tier** with no application code change — only a different model ID injected by
the tenant blueprint.

### User experience

- The player guesses a number between 1 and 100. After each **wrong** guess,
  instead of a flat "Too high"/"Too low", the feedback area shows an
  AI-generated clue prefixed with a 🤖 icon, e.g.
  `🤖 The target is an odd number that isn't prime — aim higher. (7 guesses left)`.
- A small **🤖 AI Game Host** badge appears next to the feedback the first time
  a clue is shown, signalling that clues are model-generated (the badge tooltip
  reads "Clues are generated by an Amazon Bedrock model").
- The clue is **advisory only**. The guess count, score, win/lose detection, and
  "already guessed" checks are unchanged — a clue never alters the outcome, it
  only rephrases facts the server already knows.
- The experience differs by tier:
  - **Basic tier** → **Claude Haiku 4.5**: one short, friendly sentence
    revealing a single fact (fast, low cost).
  - **Pro tier** → **Claude Sonnet 4.6**: a short, playful riddle that combines
    two facts (richer, more creative).
- If the feature is off, the model is unavailable, or the call is slow, the game
  **silently falls back** to the deterministic `too high` / `too low` text, so
  play is never blocked and no error is shown to the player.

### Technical implementation

The feature lives in `src/services/bedrockClueService.ts` and is wired into the
game engine in `src/services/gameLogic.ts`. The frontend rendering is in
`src/public/game.js` (`ai-host-badge` element in `index.html`, styled in
`styles.css`).

**1. Deterministic facts, not model guesses.** The game engine always computes
the authoritative result. When a guess is wrong and the game is still active,
`buildMoveResult()` calls the clue service with the player's `guess`, the secret
`target`, and the tenant `tier`. `buildTargetFacts(guess, target)` derives a set
of **provably true** facts about the target relative to the guess:

- `direction` — target is higher/lower than the guess
- `distance` — very close (≤5) / close (≤15) / far
- `parity` — even or odd
- `isPrime` — whether the target is prime
- `digitSum` — sum of the target's digits
- `rangeBand` — which quarter of 1–100 the target is in

Because the clue is phrased only from these facts, the model can never state
something false or reveal the exact number.

**2. Prompt construction.** `buildPrompt()` builds a strict system prompt ("you
may only use the facts provided, never reveal the number, never contradict a
fact, keep it under 30 words") plus a user message listing the facts. The tier
only changes the requested **style** (single-fact sentence for basic, two-fact
riddle for pro) — both tiers receive the same true facts.

**3. Bedrock Converse API.** `generateClue()` calls Bedrock's model-agnostic
[`ConverseCommand`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html)
(`@aws-sdk/client-bedrock-runtime`) with `maxTokens: 100` and `temperature: 0.7`.
The client is created lazily with `maxAttempts: 1` (fail fast — the game must
not wait on retries).

**4. Kept off the critical path.** The call is wrapped in
`AbortSignal.timeout(AI_HOST_TIMEOUT_MS)` (default 5000 ms). Any failure —
disabled feature, missing model ID, timeout, throttling, `AccessDenied`, or a
malformed response — is caught and logged as
`[AI Game Host] clue generation failed, falling back to plain feedback: ...`,
and `generateClue()` returns `null`. The caller treats `null` as "no clue" and
the API response simply omits the `clue` field.

**5. Configuration.** The feature is controlled entirely by environment
variables injected per tenant by the KRO `GamingApplication` blueprint:

- `AI_HOST_ENABLED` — `"true"` turns it on.
- `BEDROCK_MODEL_ID` — the model / global inference-profile ID (Haiku for basic,
  Sonnet for pro). Both tiers use a **global cross-Region inference profile**
  (`global.anthropic.claude-*`) so the same blueprint works in any supported
  Region.
- `AI_HOST_TIMEOUT_MS` — fallback timeout.

`isAiHostEnabled()` (used by `GET /api/config/status`) reports the feature as
enabled only when both `AI_HOST_ENABLED=true` and `BEDROCK_MODEL_ID` are set.

### Basic vs. Pro tenant agent

The AI Game Host is **tiered**: both tenant tiers run the exact same container
image and receive the exact same deterministic facts, but the tier decides which
Bedrock model phrases the clue and how elaborately.

| Dimension | Basic tenant agent | Pro tenant agent |
|---|---|---|
| Bedrock model | Claude **Haiku 4.5** (`global.anthropic.claude-haiku-4-5-...`) | Claude **Sonnet 4.6** (`global.anthropic.claude-sonnet-4-6`) |
| Clue style | One short sentence revealing **one** fact | A playful **riddle** combining **two** facts |
| Typical latency | ~0.9s per clue | ~1.7s per clue |
| Relative token cost | Lower | Higher |
| How it's selected | `BEDROCK_MODEL_ID` env var set by the tier blueprint | Same variable, different value |

What is **identical** across tiers: the container image, the true facts fed to
the model (`buildTargetFacts`), the authoritative game outcome (score, guesses,
win/lose), and the global cross-Region inference profile. The only real
difference is *which model phrases the clue* — a one-line configuration change in
the tier `ResourceGraphDefinition`, not a code fork.

#### Why this matters for SaaS

- **Tier differentiation drives monetization.** The Pro agent delivers a visibly
  better experience (creative, riddle-style clues from a stronger model) that
  justifies a higher price, while Basic stays cheap and fast. A premium feature
  is created by changing a model ID — no separate codebase or pipeline.
- **Cost-to-serve aligns with revenue.** Sonnet costs more per token than Haiku,
  so tenants who pay more also cost more to serve. Bedrock usage lands as its own
  line item in the Cost and Usage Report, so AI spend is **attributable per
  tenant** alongside compute and data — keeping per-tenant unit economics honest.
- **Isolation and blast radius.** Each tenant's agent uses the tenant's own Pod
  Identity role (`${tenantId}-bedrock-policy`) and network-policy egress, so one
  tenant's AI usage, throttling, or cost never leaks into another's.
- **Capability as configuration.** The differentiator lives in the kro
  `ResourceGraphDefinition`, not the app. Onboarding a Pro tenant provisions a
  more capable agent automatically from a single `Tenant` YAML commit — a small
  platform team ships tiered AI to many tenants declaratively.
- **AI is additive, never load-bearing.** Both tiers fall back to deterministic
  feedback if Bedrock is slow or unavailable, so a premium AI feature can never
  take down the core product.

### AWS access requirements

For clues to appear, the pod's IAM role (bound via EKS Pod Identity) must allow
`bedrock:InvokeModel` on the Claude foundation models and the
`global.anthropic.claude-*` inference profiles, and the tenant's network policy
egress allowlist must permit `bedrock-runtime.<region>.amazonaws.com:443`. In
the workshop these are provisioned per tenant by the `tenant-iam-role` blueprint
(a `${tenantId}-bedrock-policy`) and the `ApplicationNetworkPolicy`. On a
brand-new AWS account, Bedrock may take up to ~2 hours to finish account
verification, during which `InvokeModel` returns an "account is being verified"
error and the game uses the deterministic fallback — this is expected and
resolves on its own.

- Node.js 18+
- AWS CLI configured with credentials

- Access to AWS S3 and DynamoDB

## Local Development

### 1. Install Dependencies

```bash
npm install
```

### 2. Set Environment Variables

```bash
# Tenant Configuration (REQUIRED)
export TENANT_ID=acme-corp-001
export TENANT_NAME="Acme Corporation"
export TENANT_TIER=basic  # or 'pro'

# AWS Resources
export S3_BUCKET=your-test-bucket
export DYNAMODB_TABLE=your-test-table
export AWS_REGION=us-east-1
export PORT=8080

# AI Game Host (optional) — enable Bedrock-generated clues locally
export AI_HOST_ENABLED=true
export BEDROCK_MODEL_ID=global.anthropic.claude-haiku-4-5-20251001-v1:0  # use claude-sonnet-4-6 to mimic the pro tier
# export AI_HOST_TIMEOUT_MS=5000
```

> The AI Game Host is optional. Leave `AI_HOST_ENABLED` unset (or `false`) to run
> the game with plain higher/lower feedback. When enabled, your AWS credentials
> must allow `bedrock:InvokeModel` on the configured model.

**Tenant Tiers:**
- **Basic Tier**: Uses shared DynamoDB table (`gaming-app-shared`) with tenant isolation via partition keys
- **Pro Tier**: Uses dedicated DynamoDB table (`gaming-app-tenant-{TENANT_ID}`) for better performance and isolation

### 3. Create AWS Resources for Testing

```bash
# Create S3 bucket
aws s3 mb s3://your-test-bucket

# Create DynamoDB table
aws dynamodb create-table \
  --table-name your-test-table \
  --attribute-definitions \
    AttributeName=PK,AttributeType=S \
    AttributeName=SK,AttributeType=S \
  --key-schema \
    AttributeName=PK,KeyType=HASH \
    AttributeName=SK,KeyType=RANGE \
  --billing-mode PAY_PER_REQUEST
```

### 4. Run the Application

```bash
# Development mode with hot reload
npm run dev

# Production mode
npm run build
npm start
```

### 5. Test the Application

```bash
# Health check
curl http://localhost:8080/health

# Start a game
curl -X POST http://localhost:8080/api/game/start

# Access the UI
open http://localhost:8080
```

## API Endpoints

- `GET /` - Game UI
- `GET /health` - Health check
- `POST /api/game/start` - Start new game session
- `POST /api/game/move` - Submit game move. On a wrong guess, the response `data` includes an optional `clue` field (present only when the AI Game Host is enabled and Bedrock responds in time)
- `GET /api/game/state/:sessionId` - Get game state
- `GET /api/leaderboard` - Get top scores
- `POST /api/player/avatar` - Upload player avatar
- `GET /api/player/avatar/:playerId` - Get player avatar URL
- `GET /api/config/status` - Reports whether DynamoDB/S3 are configured, whether mock data is in use, and the AI Game Host state (`services.aiHost.enabled`, `services.aiHost.model`) plus human-readable `warnings`

### Multi-Tenant Configuration

The application supports two tenant tiers:

**Basic Tier:**
- Uses shared DynamoDB table: `gaming-app-shared`
- Tenant isolation via composite partition keys: `TENANT#{tenantId}#PLAYER#{playerId}`
- Cost-effective for smaller tenants
- Set `TENANT_TIER=basic`

**Pro Tier:**
- Uses dedicated DynamoDB table: `gaming-app-tenant-{TENANT_ID}`
- Complete table isolation per tenant
- Better performance and no noisy neighbor issues
- Set `TENANT_TIER=pro`
- Requires dedicated table to be provisioned

## DynamoDB Schema

### Basic Tier (Shared Table)

**Table Name:** `gaming-app-shared`

**Table Structure:**
- Partition Key: `PK` (String) - Format: `TENANT#{tenantId}#PLAYER#{playerId}`
- Sort Key: `SK` (String) - Format: `PROFILE` or `GAME#{timestamp}`

**Global Secondary Index (LeaderboardIndex):**
- Partition Key: `GSI1PK` (String) - Format: `TENANT#{tenantId}#LEADERBOARD`
- Sort Key: `GSI1SK` (String) - Format: `SCORE#{paddedScore}#PLAYER#{playerId}`

### Pro Tier (Dedicated Table)

**Table Name:** `gaming-app-tenant-{TENANT_ID}`

**Table Structure:**
- Partition Key: `PK` (String) - Format: `PLAYER#{playerId}`
- Sort Key: `SK` (String) - Format: `PROFILE` or `GAME#{timestamp}`

**Global Secondary Index (LeaderboardIndex):**
- Partition Key: `GSI1PK` (String) - Value: `LEADERBOARD`
- Sort Key: `GSI1SK` (String) - Format: `SCORE#{paddedScore}#PLAYER#{playerId}`
